## 0. 무엇이 달라지는가

원래 계획의 가장 약한 고리는 **"카드를 N장 쓰면 성능도 N배"라는 검증되지 않은 가정**이었다
([01-spec-review.md](01-spec-review.md) CRIT-4). 단일 카드밖에 못 쓰면 이건 끝까지 가정으로 남는다.

8장을 쓸 수 있으면 이게 **실측 곡선**이 된다. 그리고 시간이 생기면서 조건당 표본 100건 이상을
확보해 P95를 제대로 낼 수 있고, 지속 부하·메모리 포화·혼합 워크로드처럼 짧은 세션에서는
불가능했던 실험이 가능해진다.

| | 이전 (단일 카드, 2일) | 이제 (8장, 시간 단위) |
|---|---|---|
| 카드 확장 | 선형 **가정** | 1/2/4/8 **실측 곡선** |
| P95 | 표본 부족으로 보류 | 조건당 100건+ |
| 운영 한계 | 미측정 | KV 포화·스로틀링·지속 안정성 |
| 실제 서비스 형태 | prefill/decode 분리 측정만 | **혼합 부하 간섭** 측정 |
| 모델 | 1종 | 8B / 32B 비교 |

## 1. 이 프로그램이 만들어내는 것 (먼저 결정한 산출물)

측정을 먼저 정하고 결과를 나중에 해석하는 게 아니라, **어떤 질문에 답할지를 먼저 고정**하고
거기에 필요한 측정만 한다.

### D1. 용량 치트시트 — 프로젝트의 대표 산출물

읽는 사람이 5초 안에 자기 상황을 찾을 수 있는 표.

```
모델        SLA 등급        카드당 동시 사용자   카드당 출력 tok/s   먼저 막히는 것
Qwen3-8B    대화형(빠름)          ?                    ?              ?
            대화형(보통)          ?                    ?              ?
            배치(느려도 됨)        ?                    ?              ?
```

SLA 등급은 실제 서비스에서 쓰는 말로 정의한다. 예:

| 등급 | TTFT p95 | 사용자당 출력 속도 | 대표 용도 |
|---|---|---|---|
| 대화형-빠름 | ≤ 500 ms | ≥ 30 tok/s | 실시간 채팅 |
| 대화형-보통 | ≤ 1,500 ms | ≥ 15 tok/s | 일반 어시스턴트 |
| 배치 | 제한 없음 | ≥ 5 tok/s | 문서 요약, 오프라인 처리 |

**중요**: "카드당 최대 처리량"이 아니라 **"SLA를 지키면서 낼 수 있는 처리량"**이다.
전자는 운영에서 쓸 수 없는 숫자다.

### D2. SLA 완화의 대가 — 의사결정에 직접 쓰이는 곡선

> "TTFT p95 목표를 1초에서 2초로 늦추면 카드당 사용자를 몇 배 더 받을 수 있나?"

서비스 팀이 실제로 하는 협상이다. D1의 프론티어 데이터에서 그대로 나온다.
추가 측정 비용이 0이고 실무 가치가 가장 높은 산출물.

### D3. 카드 확장 효율 곡선

```
카드 수   총 처리량   카드당 처리량   확장 효율
   1          ?            ?           100%
   2          ?            ?            ?%
   4          ?            ?            ?%
   8          ?            ?            ?%
```

planner가 선형 가정 대신 이 곡선을 쓴다. 효율이 떨어진다면 **왜 떨어지는지**
(라우팅 오버헤드인가, 카드당 배치 크기 감소인가)를 데이터로 분리한다.

### D4. 병목 지도 — "무엇이 먼저 터지나"

각 운영 지점에서 한계에 가장 가까운 것이 무엇인지, 그리고 다음 한계까지 여유가 얼마인지.
후보: TTFT SLA / 출력 속도 SLA / KV 캐시 용량 / 대기열 / 전력·온도 스로틀링.

### D5. 모델 선택 가이드

8B와 32B의 카드당 용량, 필요 카드 수, 품질-비용 트레이드오프.
"32B가 2배 좋으면 카드는 몇 배 드나"에 답한다.

### D6. 아키텍처 해석 (심화)

- **Decode 유효 대역폭 역산**: 스텝당 필요한 메모리 트래픽 × 스텝/초 = 필요 대역폭 하한.
  배치를 키우면 weight 로딩이 분산되므로 이 값이 어떻게 변하는지 본다.
- **버킷 경계 효과**: 컴파일된 shape 단위로 실행되는 구조가 실제 지연에 어떻게 드러나는지.
- 두 항목 모두 **peak FLOPS 비교로는 나오지 않는** 분석이다.

## 2. 세션 설계 — 3~4시간 × 여러 번

**핵심 제약**: 서버 설정(카드 수, 모델)을 바꾸려면 `furiosa-llm serve` 재기동 + 모델 로드가 필요하고,
로드 시간은 아직 모른다. 재기동 횟수가 곧 낭비다. → **설정 하나에서 가능한 실험을 전부 끝내고 넘어간다.**

**배치 원칙**: 세션이 여러 번이므로 *각 세션이 끝날 때마다 완결된 산출물이 나오도록* 자른다.
세션 1만 끝나도 프로젝트는 성립해야 한다. 뒷 세션이 취소돼도 결과물이 남는다.

### 세션 1 (~3.5h) — 단일 카드 기반 + SLA 프론티어

| 구간 | 내용 | 누적 |
|---|---|---|
| 0:00–0:15 | **S0** Qwen2.5-0.5B 스모크. 파이프라인 검증 + **모델 로드 시간 계측** | 0:15 |
| 0:15–0:35 | **S1** 기동 (Qwen3-8B-FP8, `npu:0`) + **A1 실행 경로 확인 → input 축 확정** | 0:35 |
| 0:35–1:25 | A2 prefill 곡선, A3 버킷 경계 | 1:25 |
| 1:25–3:05 | **B1 SLA 프론티어** — 모든 산출물의 원천 | 3:05 |
| 3:05–3:30 | 여유 / B1 미완 조건 보충 | 3:30 |

**이 세션이 끝나면 나오는 것**: 용량 치트시트 v1, SLA 완화 곡선(D2), prefill 곡선, 버킷 경계 증거.
카드 확장은 아직 선형 가정이며 그 사실을 명시한다.

### 세션 2 (~3.5h) — 운영 한계 + 카드 확장

| 구간 | 내용 | 누적 |
|---|---|---|
| 0:00–0:15 | S1 재기동 (동일 설정) | 0:15 |
| 0:15–0:40 | B2 KV 캐시 포화점 | 0:40 |
| 0:40–1:05 | **B3 혼합 부하 간섭** | 1:05 |
| 1:05–1:35 | B4 soak 30분 (그동안 세션1 데이터 분석) | 1:35 |
| 1:35–3:20 | **S2·S4 확장 측정** (2장, 8장) + 여유 되면 S3(4장) | 3:20 |

**이 세션이 끝나면 나오는 것**: 확장 효율 곡선(D3) → planner의 선형 가정 제거,
병목 지도(D4), 지속 가능한 치트시트 값.

### 세션 3 (~3h, 선택) — 임베딩 + 모델 비교

| 구간 | 내용 |
|---|---|
| 0:00–0:45 | **S5** Qwen3-Embedding-0.6B |
| 0:45–2:15 | **S6** Qwen3-32B-FP8로 B1 부분집합 |
| 2:15–3:00 | 세션1·2에서 부족했던 조건 보충 |

**나오는 것**: 임베딩 용량, 모델 선택 가이드(D5).

### 세션을 나눠서 생기는 이득

모델 로드 시간을 여러 번 치르는 건 비용이지만, **세션 사이에 데이터를 분석해서 다음 세션을
조정할 수 있다.** 한 번에 몰아 하면 잘못된 축으로 6시간을 날릴 수 있다.

- 세션 1의 A1 결과로 세션 2의 input 조건을 확정한다
- 세션 1의 B1에서 SLA가 어디서 깨지는지 보고 세션 2의 확장 측정 지점을 고른다
- 세션 1에서 KV 사용률이 낮게 나오면 세션 2의 B2 범위를 넓힌다

### 세션 내 절단 순서

시간이 부족할 때 자르는 순서: **S6 → S5 → S3(4장) → B4 → B2**
절대 자르지 않는 것: **A1**(축 확정), **B1**(모든 산출물의 원천), **C1**(선형 가정 검증)

> S0에서 잰 모델 로드 시간이 15분을 넘으면 세션 2에서 S3(4장)을 생략하고 2장·8장만 잰다.
> 두 점만으로도 선형에서 벗어나는지는 판정할 수 있다.

## 3. 실험 카탈로그

전 실험 공통: warm-up 분리(기록은 유지), `--no-enable-prefix-caching`, 요청별 고유 프롬프트,
`ignore_eos`로 출력 길이 고정, `/metrics` 1초 폴링, 조건별 자기검증.

### A 티어 — 기반 (S1, ~45분)

| ID | 목적 | 조건 | 표본 |
|---|---|---|---|
| **A1** | 실행 경로 확인 → **input 축 확정** | input 128→8192, conc=1, out=1 | 조건당 10 |
| **A2** | Prefill 비용 곡선 | input 축 전체, conc=1, out=1 | 조건당 50 |
| **A3** | **버킷 경계** | input 760/768/776, 890/896/904, 1016/1024/1032 | 조건당 50 |

A1이 A2·A4의 input 축을 결정하므로 **반드시 먼저**. 1024 초과가 지원되지 않으면
범위를 좁히고 그 사실을 결과로 기록한다(은폐하지 않는다).

### B 티어 — 실무 산출물의 핵심 (S1, ~2시간)

| ID | 목적 | 조건 | 표본 |
|---|---|---|---|
| **B1** | **SLA 프론티어** — D1·D2의 원천 | input ∈ {512, 2048, 4096} × conc ∈ {1,2,4,8,16,32,64} × out=128 | **조건당 100** |
| **B2** | KV 캐시 포화점 | input=4096, conc를 포화까지 증가 (`kv_cache_usage`·`waiting_samples` 관찰) | 조건당 60 |
| **B3** | **혼합 부하 간섭** | 정상 decode 부하 중 긴 prefill 요청 주입 → decode TPOT 악화량 측정 | 25분 |
| **B4** | 지속 부하(soak) | B1의 SLA 지점에서 30분 연속 → 안정성·스로틀링·전력 | 30분 |
| **B7** | **폴링 용량-반응 시험** | 세션 1의 soak 에서 26분 지점에 처리량이 475 → 687 tok/s 로 계단 전이했다. 남아 있던 `furiosa-smi` 폴링 루프 종료 시각과 정확히 일치하나 **기전은 미확인**이다(용량-반응 비선형, 전력 신호 없음). 같은 조건에서 폴러 **0/1/2개 × 각 3분**을 재어 확정한다. 재현되면 "모니터링이 측정을 바꾼다"가 확정되고, 아니면 다른 원인을 찾아야 한다 | **10분** |

**B1이 이 프로그램의 중심**이다. 여기서 나온 격자가 치트시트, SLA 곡선, 병목 지도,
planner의 실측 테이블을 전부 만든다.

**B3이 실무 가치가 가장 높은 실험**이다. 실제 서비스는 prefill과 decode가 섞여 들어오는데,
분리 측정만으로는 "긴 문서 하나가 들어올 때 다른 사용자 응답이 얼마나 느려지는가"에 답할 수 없다.
prefill 버킷이 batch=1인 이 하드웨어에서는 특히 클 것으로 예상된다(가설).

**B4는 시간이 있어야만 가능한 실험**이다. `furiosa_smi_py`의 `ThrottleReason`
(`THERMAL_SLOWDOWN`, `HW_POWER_CAP` 등)을 함께 샘플링해서, 짧은 벤치의 수치가
30분 뒤에도 유지되는지 확인한다. 유지되지 않으면 **치트시트 숫자를 지속 가능한 값으로 낮춰야 한다.**

### C 티어 — 카드 확장 (S2~S4, 각 ~25분)

| ID | 목적 | 조건 |
|---|---|---|
| **C1** | 확장 효율 곡선 | B1의 부분집합(input=512, conc/카드 ∈ {4,16,32})을 2·4·8장에서 반복 |
| **C2** | 확장 손실의 원인 분리 | 총 동시성 고정 vs 카드당 동시성 고정, 두 방식 비교 |

C2가 중요하다. 카드를 늘리면 (a) 라우팅 오버헤드와 (b) 카드당 배치 감소가 동시에 일어난다.
**카드당 동시성을 고정한 채** 카드를 늘리면 (b)가 제거되므로 두 원인을 분리할 수 있다.

### D 티어 — 확장 (S5·S6)

| ID | 목적 | 조건 |
|---|---|---|
| **D1** | Embedding | Qwen3-Embedding-0.6B, batch ∈ {1,2,4,8,16,32,64} × 문장 길이 2종 |
| **D2** | 모델 비교 | Qwen3-32B-FP8로 B1 부분집합 반복 → 카드당 용량 비교 |

## 4. 새로 추가하는 분석

### 4.1 SLA 프론티어에서 운영점 찾기

B1 격자에서 각 (모델, input, output)마다:

```
C_max(SLA) = TTFT_p95(c) ≤ SLA_ttft  이고
             per_user_tps(c) ≥ SLA_tps  를 만족하는 최대 concurrency c

카드당 용량 = aggregate_output_tps(C_max)
```

**최대 처리량 지점이 아니라 SLA를 만족하는 최대 지점**을 쓴다. 둘은 보통 다르고,
전자를 쓰면 용량을 과대평가한다.

### 4.2 SLA 민감도

```
민감도 = C_max(느슨한 SLA) / C_max(빡빡한 SLA)
```

"TTFT 목표를 2배 늦추면 사용자를 X배 더 받는다"를 숫자로 만든다.

### 4.3 확장 효율

```
효율(n) = 총처리량(n장) / (총처리량(1장) × n)
```

C2 데이터로 손실을 라우팅 오버헤드와 배치 감소로 분해한다.

### 4.4 Decode 유효 대역폭 역산

```
스텝당 최소 트래픽 ≈ (파라미터 바이트 / tp) + (batch × context_len × 토큰당 KV 바이트)
필요 대역폭 하한  = 스텝당 트래픽 × (스텝/초)
```

배치를 키울수록 weight 로딩이 분산되므로 이 값의 변화가 **memory-bound에서 벗어나는 지점**을
보여준다. HBM 카운터가 없어도 실측 tok/s만으로 계산 가능하다.

> 주의: 이건 **하한**이다. "실측이 스펙 대역폭의 X%" 같은 표현은 쓰되,
> "따라서 NPU가 비효율적"이라는 결론으로 넘어가지 않는다.

### 4.5 병목 판정

[01-spec-review.md](01-spec-review.md) IMP-7(b)의 규칙표에 B2·B4에서 얻는 항목을 추가한다.

| 관측 | 판정 |
|---|---|
| `kv_cache_usage` 100% 근접 + `waiting_samples` 증가 | `memory_capacity` |
| `running_samples` < 요청 동시성 + 대기열 증가 | `concurrency_scheduling` |
| B4에서 `ThrottleReason` 발생 | `thermal_or_power` |
| B3에서 prefill 주입 시 decode TPOT 급증 | `prefill_interference` |
| 어느 것도 아님 | **`unknown`** (억지 분류 금지) |

## 5. planner 업그레이드

| 항목 | 이전 | 이후 |
|---|---|---|
| 카드 수 계산 | 선형 가정 + 고정점 반복 | **실측 확장 곡선** + 고정점 반복 |
| 카드당 용량 | 최대 처리량 | **SLA 프론티어의 운영점** |
| 병목 출력 | 4분류 추정 | 실측 규칙표 기반 + `unknown` 허용 |
| 경고 | 범위 밖 저신뢰 | + 버킷 경계 경고, + 지속가능성 경고(B4 미달 시) |
| 신규 출력 | — | **"SLA를 이만큼 완화하면 카드 N장을 아낍니다"** |

마지막 항목이 이 도구를 계산기에서 **의사결정 도구**로 만든다.

## 7. 리스크

| 리스크 | 대응 |
|---|---|
| 모델 로드가 예상보다 오래 걸림 | S0에서 측정 후 세션 수를 줄인다. 판단 기준을 미리 고정(§2) |
| 1024 초과 prefill 미지원 | A1에서 즉시 확인. input 축을 좁히고 **한계로 기록** |
| 8B 아티팩트가 dp 확장을 지원하지 않음 | C 티어를 tp/pp 비교로 대체. 안 되면 선형 가정을 **한계로 명시** |
| 32B가 카드 1장에 안 올라감 | 필요 카드 수 자체가 결과다. 그대로 기록 |
| soak에서 성능 저하 | **치트시트 숫자를 지속 가능한 값으로 낮춘다.** 짧은 벤치 값을 쓰지 않는다 |
| 예약 시간 초과 | §2의 절단 순서를 따른다 |

## 8. 유지되는 원칙

8장이 생겨도 바뀌지 않는 것들.

- 확인되지 않은 SDK 동작을 가정하지 않는다
- 측정·계산·UI를 분리한다
- 데이터를 가설에 맞추지 않는다 — A1/A3/B3 결과가 예상과 다르면 서사를 바꾼다
- 결과가 나오기 전에 결론을 쓰지 않는다
- "peak FLOPS 대비 낮음 = 비효율" 같은 결론을 내지 않는다
- 실측 범위를 벗어난 추정에는 저신뢰 경고를 붙인다
