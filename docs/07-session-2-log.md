## G4. ★★ 가장 큰 것 — 1장 곡선의 TTFT 가 다중 카드로 전이되지 않습니다

검증 세션 지적을 원본으로 확인했고, **fill 구간 아티팩트가 아닙니다.** 구간별로 전부 평탄합니다.

```
카드당 32 (8장 총 256)          카드당 32 (1장)
  구간      p50      p95          구간      p50      p95
  0-60    480.2   1012.7          0-60    159.4    237.9
 60-120   401.9    907.2         60-120   158.7    236.1
120-180   386.1    934.2        120-180   159.1    162.8
180-240   464.2   1015.3        180-240   158.8    162.5
240-300   502.9   1068.9        240-300   159.0    162.6

카드당 16 (8장 총 128)          카드당 16 (1장)
  0-60    223.8    318.4          0-60    154.0    230.6
240-300   223.6    313.6        240-300   154.1    157.4
```

**정상상태 비교:**

| 카드당 동시성 | 1장 p95 | 8장 p95 | 배수 |
|---:|---:|---:|---:|
| 16 | 157.4 ms | 313.6 ms | **2.0×** |
| 32 | 162.6 ms | 1,068.9 ms | **6.6×** |

**비율(`peak_running/requested`)은 8장 두 조건 모두 1.00 입니다** — 서버는 요청한 동시성을
다 물고 있는데 첫 토큰만 늦습니다. 부하가 클수록 배수가 커집니다.

### 왜 커밋 차단인가

**planner 는 1장 곡선의 TTFT 로 SLA 를 판정한 뒤 카드 수를 곱합니다.** 그런데 치트시트가
권하는 배포는 20~63장입니다.

```
대화형-빠름  "TTFT p95 <= 0.3s"  ← 1장 측정 157~163ms 로 통과 판정
             그런데 8장 카드당16 에서 이미 313.6ms  → 위반
             8장 카드당32 에서는 1,068.9ms          → 3.5배 위반
```

**즉 치트시트의 지연 SLA 판정이 다중 카드 배포에서 성립하지 않습니다.** 이건 값 하나가
틀린 게 아니라 **모델(1장 곡선 × 카드 수)이 지연에 대해 틀렸다**는 뜻입니다.

기전 미상(라우터 큐잉? 공유 HTTP 서버?). **2장·4장을 재면 카드 수에 따른 증가 곡선이
나옵니다** — D4 의 우선순위가 다시 올라갑니다.

> 처리량은 1장 × 카드 수가 잘 맞았습니다(카드당 32 에서 100.5%). **지연만 안 맞습니다.**
> 그래서 지금까지 안 보였습니다 — 확장효율은 처리량으로만 정의돼 있습니다.
