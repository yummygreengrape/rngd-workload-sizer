## 발생한 문제와 대응

### 문제 1 — A3 마지막 조건에서 하네스가 죽음

`in=2048` 조건에서 `CalibrationError: 토큰 수를 셀 수 없습니다`.

**원인**: 프롬프트 길이 보정에 쓰는 `/tokenize` 호출이 한 번 실패하면
`calibrate()` 가 즉시 하드 실패했다. keep-alive 커넥션이 끊긴 것으로 보이는데,
`tokenize_count()` 가 비정상 응답에서 커넥션을 버리지 않아 이후 호출이 계속 같은 죽은
커넥션을 썼고, 재시도도 폴백도 없었다.

**영향**: A3의 21개 조건 중 20개는 정상 저장됨(`requests.jsonl` 은 증분 기록).
2048 조건만 유실 → 별도 실행으로 확보(173.3 ms).

**수정**:
1. `tokenize_count()` 가 비정상 응답에서도 커넥션을 버려 다음 호출이 재연결되게 함
2. 토큰 카운터가 실패 시 **1회 재시도 → 그래도 안 되면 probe 요청으로 폴백**
3. 재시도·폴백 횟수를 `meta.json` 에 기록

측정 도중 하드 실패는 시간이 한정된 세션에서 가장 비싼 종류의 버그다.

### 문제 2 — 표본 부족 경고 (설계대로 동작)

A1·A3는 조건당 10~30건이라 P95 기준(100건) 미달 경고가 떴다.
prefill 스캔은 P95가 목적이 아니므로 config 에서 `min_samples_for_p95` 를 낮춰 대응.
B1은 조건당 100건으로 실행.

## C1/C2 — 카드 확장 (20:26~20:42)

### 측정창 길이가 결과를 바꾼다 — 방법론 교훈

처음 C1을 조건당 100건으로 돌렸더니 8장 conc=128과 conc=256의 처리량이
4829 / 4822 tok/s로 **동일**하게 나왔다. 측정창이 2.7초뿐이라 정상상태가 없었기 때문이다.

요청 수를 늘려 측정창을 14.7초로 만들자 conc=256이 **7003 tok/s — 45% 증가**했다.
동시에 클라이언트 CPU를 관찰해 상위 프로세스가 `furiosa-llm`(서버, 893%)임을 확인했다.
부하 생성기 병목이 아니다.

→ **모든 카드 수에서 측정창 15초 이상**이 되도록 요청 수를 맞춰 C2로 재측정했다.
→ 이후 조건 설계에 "측정창 하한"을 넣어야 한다.

| 카드당 동시성 | 1장 | 2장 | 4장 | 8장 |
|---:|---:|---:|---:|---:|
| 4 | 274.3 (100%) | 550.7 (**100.4%**) | 1095.1 (**99.8%**) | 2125.7 (**96.9%**) |
| 16 | 707.1 (100%) | 1411.1 (**99.8%**) | 2895.3 (**102.4%**) | 5702.1 (**100.8%**) |

8장까지 97~102%를 유지한다. 카드당 동시성 32에서 8장일 때만 82.1%로 떨어진다.

> ⚠️ 단, 82.1% 지점의 측정창이 14.6초로 이번 비교군 중 가장 짧다. 측정창이 결과를 바꾼

> "8장·고동시성에서 효율 저하 가능성"으로만 적는다.

### 검증기 버그 — dp 배포에서 동시성 오판

`/metrics` 의 `furiosa_llm_num_requests_running` 은 **엔진별로** 나온다
(`{engine="0"}`, `{engine="1"}`, …). 검증기가 최댓값을 쓰고 있어서 dp=8에서
총 동시성 256을 "한 엔진의 32"와 비교해 **항상 큐잉으로 오판**했다.
엔진별 값을 합산하도록 `peak_sum()` 을 추가해 수정.

### 또 하나 — metric 조회가 run 전체를 훑고 있었음

`poller.peak()` 이 run 시작 이후 **모든** 샘플을 보고 있어서, B1의 KV 사용률이
조건별 값이 아니라 **누적 최댓값**으로 기록됐다(conc=64 다음 조건들이 전부 0.1442로 고정).

남아 있어 **기존 데이터도 사후 재계산 가능**하다.

## ⚠️ 정정 — 측정창 길이가 지연 통계까지 왜곡하고 있었다

처리량에서 발견한 측정창 문제가 **지연 백분위에도 똑같이 적용된다**는 것을 뒤늦게 확인했다.
앞서 B1 결과로 적은 "최대 처리량의 대가는 TTFT p95 3초" 라는 서술은 **상당 부분 아티팩트다.**

같은 조건(1 RNGD, in=512, out=128, conc=32)을 두 번 측정한 결과:

| run | 측정 요청 | 측정창 | agg tok/s | **TTFT p95** |
|---|---:|---:|---:|---:|
| B1 | 100 | 13.7 s | 936.8 | **1,436.9 ms** |
| C2x1 | 500 | 60.0 s | 1,065.9 | **251.6 ms** |

**원인**: 짧은 창에서는 시작 시점에 32개 요청이 한꺼번에 도착하는 램프업 구간이
전체 표본의 상당 비율을 차지한다. 그 구간의 큐 대기가 p95를 지배한다.
정상상태에 도달한 뒤의 지연은 훨씬 낮다.

처리량도 같은 방향으로 왜곡된다(짧은 창 → 과소평가). 지연은 반대로 **과대평가**된다.
