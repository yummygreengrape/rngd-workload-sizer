## 5. RNGD 실측 세션 1 (2026-08-25 20:00~21:22)

**목적** 실측 기반 capacity 데이터 확보.

**결과** 18 run / 117MB

| 실험 | 얻은 것 |
|---|---|
| A1 실행 경로 | **8192 토큰 프롬프트 정상 동작** → input 축 제약 없음 (CRIT-1 해결) |
| A3·A4 계단 스캔 | **prefill이 계단형**. 257–1024 토큰이 동일 비용(~78ms). 경계에서 토큰 몇 개 차이로 +24% |
| B1·B1hi 프론티어 | 동시성별 처리량/지연 곡선. **절벽은 conc 128↔256** (입력 512 기준. 세션 2 단독 재측정으로 확정) |

**측정 방법론 결함 3건 발견·수정**

- 다른 측정과 동시 실행 시 처리량 -26% (부하 생성기의 호스트 자원 경합)
- dp 배포에서 엔진별 metric을 합산하지 않아 동시성 항상 오판

→ 데이터가 `window_s`·`exclusive`를 스스로 싣고, planner가
**신뢰 창 → 단독 실행 → 창 길이** 순으로 근거를 고르게 함.

## 7. planner 테스트 (A1) — 완료

**목적** 눈으로만 확인하다 버그 3건을 놓쳤다. 기획서가 "capacity 테스트를 구현보다 먼저"라고
했는데 순서가 뒤집혔으므로 복구한다.

**결과** `tests/test_benchmark_store.py` 35건 + `tests/test_capacity.py` 44건 = **79건 추가**
(전체 137건 통과).

검증 범위
- 단위 일관성 (`users × tok/s`, `required / capacity`)
- `target_utilization` **한 번만** 적용 · headroom 변환 · 예상 이용률에 재적용 안 함
- 올림 처리 (1.01장 → 2장, 정확히 맞으면 올리지 않음, 0장 금지)
- 처리량만으로 "충분" 판정 금지 · 사용자당 속도·E2E p95도 독립 검사
- P95 표본 부족 시 통과시키지 않음
- 고정점 수렴 · **발산 시 무한루프 방지와 경고**
- 출처 게이팅 (호스팅 거부 / mock 명시 허용 / 혼합 표시)
- 측정 신뢰도 우선순위 (신뢰 창 → 단독 실행 → 창 길이)
- 버킷 경계 판정과 "조금 줄이면 같은 비용" 조언
- 운영점이 **동시성 최대가 아니라 처리량 최대**를 고르는가
- 병목 판정 규칙과 `unknown` 허용

**부수 성과** 테스트를 쓰다 실측 회귀에서 200명 시나리오가 15장 → **11장**으로 개선됨
(conc=64 근거가 B1hi 로 바뀐 결과).

**발견한 것** 카드당 처리량이 동시성에 **정확히 비례**하면 카드를 늘려도 총 처리량이
늘지 않아 고정점이 발산한다 (`N × k·(users/N) = k·users`). 실제로는 처리량이 포화하므로
카드를 나누는 것이 이득이 된다. 발산 케이스를 테스트로 고정했다.

## 10. 교차검증 F1 반영 — 카드 수 추론 (2026-08-26)

**지적** (검증 세션 `puriosa-project-c4`): `analysis/process.py` 가 **실험 코드 이름 표**로
카드 수를 추론한다. 표에 없는 코드로 측정하면 그 데이터가 조용히 버려진다.

**직접 확인한 것**
- `process.py` 의 hosted 행 7 vs 원본 19 — E4 조건 12개가 "카드 수 불명" 으로 탈락
- `B1hi`·`B4soak2` 는 표에 없는데 살아남았는데, `--cards` 플래그로 `meta.n_cards` 가
  기록됐기 때문. E4 는 그 플래그 이전 측정이라 양쪽 다 없어 탈락
- **다음 세션 예정 코드 `B2`·`B3`·`D1emb` 도 전부 표에 없다** ← 이게 진짜 위험

**수정**

카드 수 조회를 3단으로 바꿨다. 순서가 곧 신뢰도 순이다.

1. `meta.target.n_cards` — 하네스가 `--cards` 로 기록한 값
2. 서버 기동 로그의 `Device mesh: N DP group(s)` — base_url 의 포트로 대조.
   같은 포트가 서로 다른 구성으로 쓰였으면 **추측하지 않고 불명 처리** (8000 번을
   1장 서버와 8장 서버가 번갈아 썼다)
3. 이름 표 — 최후 수단

그리고 두 가지를 더 넣었다.

- **출처 게이트를 카드 수 확인보다 앞에.** hosted 는 카드 수라는 개념 자체가 없으므로
  "카드 수 불명" 으로 버리면 이유가 틀리다. 행은 남기되 카드 수를 위장하지 않는다
  (`n_cards_known: false`, `card_source: "정의되지 않음 (hosted)"`).
- **실측 데이터가 버려지면 크게 알린다.** `process.py` 가 경고를 찍고 exit 1 을 낸다.
  측정 세션 하나를 통째로 날릴 수 있는 실패라 조용히 넘어가면 안 된다.

**검증**

| | 이전 | 이후 |
|---|---|---|
| hosted 행 | 7 | **19** (원본과 일치) |
| measured_local 행 | 87 | **87** (유실 없음) |
| 건너뜀 | 12 | **0** |
| 카드 수 출처 | 이름 표 전량 | server_log 80 / legacy 9 / meta 5 / hosted 12 |

서버 로그 유래 카드 수를 이름 표와 대조해 **불일치 0건**, 프론티어 9개 값과
확장 효율 3개 값이 **모두 이전과 동일**함을 확인했다. 회귀 없음.

회귀 테스트 24건 추가 (`tests/test_process.py`) — 전체 163건.

- 게다가 **루프 반송 상태 버그**가 있었다. `cards` 를 조건 루프 안에서 덮어쓰는데 선언은 run 단위라,
  첫 조건이 자리표시를 넣으면 다음 조건부터 판정이 뒤집힌다. E4 12행 중 **10행이 known=true** 였다.

수정: `hosted = source != "measured_local"` (출처만으로 판정) + 조건별 지역 변수로 분리.

| | 이전 | 이후 |
|---|---|---|
| hosted 행 판정 | E1 known=true / E4 2행 false, 10행 true | **19행 전부 known=false** |
| legacy_table 의존 | 9행 | **2행** (S0 스모크만) |

프론티어 9개 값·확장 효율 3개 값 동일. 회귀 테스트 4건 추가.

**F3 — soak 폴링 해석: 미확인으로 하향.** 반증 두 가지가 타당했다.

## 12. 교차검증 라운드 5 — 가장 큰 발견 (2026-08-26)

**F9 — "측정창 길이" 는 원인이 아니라 대리지표였다.**

검증 세션이 긴 측정을 앞에서 잘라 "짧게 쟀다면" 을 재현하다 찾았다. 시간으로는 설명이 안 됐다
— 창 15초인데 수렴한 측정이 있고, 창 45초인데 p95 오차 +178% 인 측정이 있었다.

진짜 변수는 **warm-up 요청 수가 동시성보다 적은 것**이다. 워커 N개에 warm-up 이 M건(M<N)이면
워커 N−M 개의 **첫 요청이 측정에 들어오고**, 그것들은 큐가 형성되는 동안 대기한다.
그 수는 **고정(=동시성)** 이라 오래 측정해도 줄지 않고 희석될 뿐이다.

| 조건 | warm-up | 동시성 | 앞 N건 중앙값 | 이후 | 배율 |
|---|---:|---:|---:|---:|---:|
| C2x2 | 16 | 8 | 151.7 | 150.2 | 1.0× |
| C1x8b | 32 | 32 | 163.7 | 149.0 | 1.1× |
| B1hi | 64 | 64 | 253.9 | 173.9 | 1.5× |
| C2x1 | **8** | **32** | 853.3 | 159.1 | **5.4×** |
| B1hi | **64** | **128** | 3,774.9 | 267.3 | **14.1×** |

**결정적 검증** — B1 conc=32(warmup 8, 측정 100건). 앞 8건·16건 제외로는 복원 안 되고
**정확히 동시성만큼(32건)** 빼야 p95 1,437ms → 246.5ms 로 참값(252ms)이 복원된다.

### 바뀐 것

| | 이전 | 이후 |
|---|---|---|
| 진단 | 측정창이 짧아서 | warm-up 이 동시성보다 적어서 |
| 대응 | 더 오래 측정 | `warmup_requests >= concurrency` (자동 상향) |
| 기존 데이터 | 재측정 필요 | **앞 동시성만큼 제외해 복구** (23개 조건) |
| 판정 기준 | `MIN_TRUSTED_WINDOW_S = 15` | warm-up ≥ 동시성 **그리고** 표본 ≥ 동시성×20 |

**결과가 크게 바뀌었다.** conc=128 의 TTFT p95 가 **5,324ms → 284.8ms**.
절벽이 64↔128 이 아니라 **128↔256** 이었다. README 서사를 다시 썼다 —
대화형에서 먼저 걸리는 것은 첫 응답이 아니라 **사용자당 생성 속도**다.

**F7 — 아티팩트 버킷 8개 중 3개만 실제 비용 경계.**

내가 "실측 계단이 257·1005 라 어긋난다" 고 했는데 **방향이 반대**였다. 그건 목표 길이로 본
것이고, 실제 토큰 수로 재정렬하면 계단이 정확히 128·256·1024 다. 문제는 384·768·896 주변이

→ `MEASURED_COST_EDGES` 로 교체(모델별, 실측 없으면 아티팩트로 폴백).

**F8 — 평탄 구간이 256–1,004 가 아니라 256–1,023.** 4.0배(3.5배 아님). README 6곳·그래프 정정.

**B3 설계 — 길이 편향 지적 반영.** 주입에 느려진 요청은 더 오래 살아 겹칠 확률이 높다.

# 주요 실측 수치 (현재 근거)

**용량 치트시트** — RNGD 1장, Qwen3-8B-FP8, 입력 512 / 출력 128

**SLA 를 만족하는 최대 카드당 동시성** — 이 표는 "지연 제약만" 본 값이다.

| SLA 등급 | 조건 | 카드당 동시 사용자 | 그 점의 카드당 tok/s |
|---|---|---:|---:|
| 대화형-빠름 | TTFT p95 ≤0.3s, 사용자당 ≥30 tok/s | 16 | 702 |
| 대화형-보통 | TTFT p95 ≤1.5s, 사용자당 ≥15 tok/s | 63 | 1,213 |
| 배치 | TTFT 제한 없음, 사용자당 ≥5 tok/s | 250 | 1,365 |

> 배치의 250 은 **TTFT p95 9.1초**인 점이다. 처리량 최대는 conc **128** (1,564 tok/s)
> 이고 planner 는 운영점으로 이쪽을 고른다 — 동시성 최대를 고르면 처리량이 오히려 준다.
>
> ⚠ **이 표는 1장 배포 기준이다.** 8장 배포에서는 같은 카드당 동시성의 TTFT p95 가
> 2.0~6.6배로 나온다 (카드당 16 에서 157.6 → 313.6ms, 32 에서 162.6 → 1,068.9ms).
> 다중 카드 배포의 지연 판정은 아직 근거가 없다.

**필요 카드 수** (동시 사용자 1,000명, 이용률 70%): 빠름 **63장** / 보통 **22장** / 배치 **6장**

빠름은 **지연이**, 나머지 둘은 **처리량이** 카드 수를 결정한다. TTFT 를 무제한으로 풀어도
카드 수는 안 줄고(63 → 63), 63 → 22장의 감소는 전부 사용자당 속도를 30 → 15 tok/s 로
낮춘 데서 온다.

> 세션 2 재측정으로 빠름이 55 → 63장이 됐다. 카드당 32 의 사용자당 속도 중앙값이
> **29.7 tok/s** 로 30 을 못 넘는데(요청의 62.5% 가 미달), 이전 근거였던 세션 1 측정은
