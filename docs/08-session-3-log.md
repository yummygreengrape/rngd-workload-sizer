## 승인 상한은 입력 길이를 따라 오른다 (관측, 이유 미상)

`kv_cache_peak` 원측정값이 단조 상승한다. **환산 편향이 아니다.**

```

in= 1024   0.422  0.430                   0.4260
in= 2048   0.442  0.443  0.447  0.450     0.4455
in= 4096   0.455
in= 6144   0.463
in= 8192   0.472
```

상승이 감속한다(배증당 +0.0285 → +0.0195 → +0.0095 → +0.0085). **0.48~0.50 근처 점근선으로 보이나
6점이라 곡선은 맞추지 않는다.**

`peak_running × (입력+출력)` 환산은 모든 요청이 출력을 다 생성한 상태를 가정하는 과대추정이므로
**`kv_cache_peak` 를 1차 지표로 쓰고 토큰 환산은 참고로만 둔다.** 폭은 어느 쪽으로 봐도 안 좁아진다
(kv 19.4% / 토큰환산 17.5%).

1. **§1 을 "네 점" 이라고 보고했다.** `s3_x3.log` 이 8장인 줄 알았으나 4장 run 이었다.
   8장 열은 세션 2 데이터다. → 2→4장 동일세션 비교로 대체.
2. **§4-1 승인 건수 추정(16.3/11.9)이 틀렸다.** 실측 21/16.
   `mean_decode_inflight/0.91` 의 0.91 을 in=2048 에서 교정해 놓고 in=6144·8192 에 썼다.

   경고 방향까지 반대로 달았다("더 낮을 수 있다" → 실제로는 더 높았다).
3. **"conc=96 이 이미 절벽이라 C=118,000 을 반증한다" 가 틀렸다.** peak 96/96 으로 안 잘렸다.
   in=1024 상한은 (110,592, 122,112] 이고 118,000 이 그 안에 있다. 반증 철회.
4. **§1 을 전체평균으로 계산했다.** 정상상태로 맞추면 4장이 100% 위로 올라온다.
   창 길이가 조건마다 달라 과도 비중이 다른 게 원인 — 오늘 세 번 걸린 함정이다.
5. **A1solo 가 "7~8% 느리게 돌았다" 고 읽었다.** 틀렸다. A1solo 수준(~1205)은
   S3x1 의 **정상상태**(1212.0)와 0.6% 차이다. S3x1 에만 과도가 있었을 뿐이다.
   비교 기준을 과도 구간으로 잡아서 해석이 뒤집혔다.
6. **S3cliff 를 시간에 쫓겨 얕게 쟀다** (창 100s, 유지율 0.91). 세션 1 과 같은 실수.
